The money path, the refresh-token rules and the ticket-import path are in good shape and were
checked closely — the wallet debit/refund ledger, idempotency, reuse detection and the blob-key
ownership model all hold up. What is left clusters in three places: **the map WebView's browser
security posture**, **the TransitInfoAPI ↔ GetThereAPI boundary**, and **the GTFS import's
transaction handling**.

## 🔴 High

### H1. The map page holds a bearer token, has no CSP, and loads script from a third-party CDN

`GetThereAPI/Program.cs:289` · `GetThereAPI/wwwroot/map/public.html:7-8`

The CSP in `OnPrepareResponse` returns early for anything not under `/admin`:

```csharp
if (!ctx.Context.Request.Path.StartsWithSegments("/admin")) return;
```

So `/map/public.html` — the page `MapPage.xaml.cs:51` hands a live access token to via
`window.setAuthToken(...)` — is served with **no** `Content-Security-Policy`, `X-Content-Type-Options`,
or `frame-ancestors`. It then pulls executable JavaScript from an external origin with no
subresource integrity:

```html
<script src="https://unpkg.com/maplibre-gl@4.7.1/dist/maplibre-gl.js"></script>
```

Anything that origin serves runs with access to `authToken`. No `integrity=` attribute exists on any
CDN reference anywhere in either project's `wwwroot`. `/map` is additionally the one path with
`AllowAnyOrigin` CORS (`Program.cs:275-277`) and the page explicitly supports being framed
(`public.html:74`), with no `frame-ancestors` to bound it.

**Fix:** extend the header block to `/map`, vendor MapLibre locally (or add SRI + pin), and set
`frame-ancestors` deliberately rather than by omission.

### H2. XSS in the map sidebar from feed-supplied text

`GetThereAPI/wwwroot/map/public.html:455, 471, 489` and the identical `map/index.html` (byte-identical
to `TransitInfoAPI/wwwroot/map/index.html`)

The page has an `esc()` helper and uses it for `props.name` and `props.countryName`, but not for the
departures block, which is built from GTFS data the operator controls:

```js
depHtml += `<div class="departure-item"><strong>${time}</strong> ${d.headsign ? d.headsign + ' — ' : ''}${d.routeName || ''}${delay}</div>`;
document.querySelector('.departures').innerHTML = depHtml;
```

`headsign` and `routeName` are free text out of `trips.txt` / `routes.txt`. `${rt || '-'}` (line 455)
and `${props.routeType || '-'}` (line 489) are also unescaped. Combined with H1 — no CSP, token in a
page variable — a hostile or compromised feed reaches the user's access token.

**Fix:** `esc()` those three interpolations; H1's CSP is the backstop, not the fix.

### H3. TransitInfoAPI rate-limits every caller by IP, and GetThereAPI is one IP

`TransitInfoAPI/Program.cs:160-168`

```csharp
partitionKey: context.Connection.RemoteIpAddress?.ToString() ?? "unknown",
PermitLimit = 100, Window = TimeSpan.FromMinutes(1)
```

Every request GetThereAPI's map proxy makes arrives from a single address, so **all app users share
one 100/minute bucket**. A handful of people panning a map exhausts it; `TransitInfoApiClient` maps
the resulting 429 to `502 TRANSIT_UPSTREAM_UNAVAILABLE` with no retry or backoff, so the map simply
reports the service as down.

GetThereAPI already solved exactly this and documents why (`GetThereAPI/Program.cs:163-183`:
partition on the authenticated user first, fall back to IP only for anonymous callers). That fix was
never applied here, and the limits here are hardcoded rather than configurable as they are there.

### H4. The 401-retry path re-sends an already-sent `HttpRequestMessage`

`GetThereAPI/Services/TransitInfoApiClient.cs:192-201`

```csharp
var response = await _httpClient.SendAsync(request, ct);
if (response.StatusCode == HttpStatusCode.Unauthorized)
{
    InvalidateCachedToken();
    request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", await GetAccessTokenAsync(ct));
    response = await _httpClient.SendAsync(request, ct);   // same instance
}
```

`GetRawAsync` two methods up builds a **fresh** `HttpRequestMessage` for its retry (line 167) and
disposes the first response — so the asymmetry looks like an oversight rather than a decision. Every
caller that goes through `SendWithAuthAsync` (`/stations`, `/routes`, `/realtime/vehicles`,
`/realtime/alerts`, `/mobility/stations`, and all of `FetchAllPagesAsync`) takes this path when the
service-account token lapses. Additionally **no response in this method is ever disposed**, including
the discarded 401 and every page in the paging loop.

*Confirm by compiling/running:* whether the runtime rejects the re-send is version-dependent; the
undisposed responses are unconditional.

### H5. A ticket-file upload cannot survive a token refresh

`GetThere/Helpers/AuthenticatedHttpHandler.cs:53-55` · `GetThere/Services/ImportedTicketService.cs:126`

The handler's 401 retry rebuilds the request by re-reading the original content:

```csharp
if (request.Content is not null)
    requestBodyBytes = await request.Content.ReadAsByteArrayAsync(cancellationToken);
```

`UploadAsync` sends a `MultipartFormDataContent` wrapping a `StreamContent` over the picker/camera
stream. That stream is consumed by the first send, so the re-read throws, gets swallowed by
`catch (Exception ex)` at line 139, and the user sees a generic "Could not read that file" instead of
a retried upload. It fails precisely when the access token expired mid-import — the case the retry
exists for. JSON bodies are unaffected (buffered).

**Fix:** buffer the file into a `ByteArrayContent` before sending, or make the handler skip the retry
for non-buffered content and surface a clear error.

## 🟠 Medium

### M1. The GTFS import transaction is never disposed and EF's reference is never cleared

`TransitInfoAPI/Managers/FeedManager.cs:569-587, 1228`

`BeginImportTransactionAsync` calls `_db.Database.UseTransaction(sqlTx)`, and nothing ever calls
`UseTransaction(null)` — grep confirms the call does not exist anywhere in the solution, though
`audit.md` records it as a previous fix (TransitInfoAPI item 16). Consequences:

- `FinalizeVersionPhaseAsync` commits at line 1228 and then issues four more `ExecuteSqlRawAsync`
  statements (1235-1255) plus `MatchPlacesAsync`, all while EF still holds the completed transaction.
- Three early-return paths (`ImportFeedVersionAsync:390`, `:395`, and the validation-failure return)
  leave the method with the transaction committed inside a helper and no disposal on the way out.
  There is no `finally` around `sqlConn`/`sqlTx` at all.
- `BeginImportTransactionAsync` branches on `_db.Database.CurrentTransaction is not null` and
  **reuses** it. A second import through the same scoped `FeedManager` therefore runs against a
  committed transaction. Today's callers happen to use one scope per import
  (`FeedPollingWorker.cs:69`, one HTTP request per manual trigger), so this is latent — but it is one
  refactor away from live.

### M2. Reconciliation runs inside the import's SQL transaction

`TransitInfoAPI/Managers/FeedManager.cs:415`

`ReconcileAndBackfillAsync` — which itself runs `ReconcileFeedVersionAsync` plus a `StopTimes`-wide
`UPDATE` with a 600 s command timeout — is called between `BeginImportTransactionAsync` and the
commit. `audit.md` records this as moved outside the transaction in a previous session; it is back
inside. A national-scale feed holds import locks for the whole reconciliation pass.

### M3. Per-trip `LogInformation` in the realtime poll loop, plus leftover debug output

`TransitInfoAPI/Managers/RealtimeManager.cs:233-235, 250-251`

One `Information`-level line per trip update, per feed, per poll:

```csharp
_logger.LogInformation("RT PARSE: feed={FeedId} trip_id={TripId} routeId=... sampleDelays={Delays}", ...);
```

and immediately below, debug scaffolding that was never removed:

```csharp
_logger.LogInformation("RT feed {FeedId}: {Count} trip_ids. Contains 0_2_201_2_21154? {Has}",
    feed.FeedId, tripUpdates.Count, tripUpdates.ContainsKey("0_2_201_2_21154"));
```

A hardcoded trip id from someone's debugging session, evaluated and logged on every poll of every
feed forever.

### M4. Alerts with no end time are never purged

`TransitInfoAPI/Managers/RealtimeManager.cs:317-320`

```csharp
await db.Alerts.Where(a => a.ActivePeriodEnd != null && a.ActivePeriodEnd < cutoff).ExecuteDeleteAsync(ct);
```

GTFS-RT alerts routinely carry no `ActivePeriod` end. Those rows are inserted and never deleted, and
the poll re-reads every alert for the feed each cycle (line 261) to dedupe against them.

### M5. Alert filtering substring-matches a comma-joined id list

`TransitInfoAPI/Managers/RealtimeManager.cs:399-402`

```csharp
query = query.Where(a => a.AffectedStopIds != null && a.AffectedStopIds.Contains(stopOnestopId));
```

`AffectedStopIds` is `string.Join(",", ...)`. Stop `123` matches an alert affecting `1234`, and the
filter is non-sargable on top of that. Same for `AffectedRouteIds`.

### M6. GetThereAPI never records `LastLogin`

`GetThereAPI/Managers/AuthManager.cs:86-111`

TransitInfoAPI sets it (`TransitInfoAPI/Managers/AuthManager.cs:65`); GetThereAPI does not. The
column is read by `AdminManager.cs:51` and `RolePermissionManager.cs:152` and surfaced in
`UserListItem.LastLogin` / `UserDto.LastLogin`, so the admin console's "Last login" is permanently
blank for every GetThereAPI user.

### M7. Seeding ignores whether the admin account was actually created

`GetThereAPI/Program.cs:385-396` · `TransitInfoAPI/Program.cs:376-388, 412-422`

```csharp
await userManager.CreateAsync(admin, pwd);
await userManager.AddToRoleAsync(admin, RoleNames.Admin);
```

The `IdentityResult` is discarded in all three places (both admin seeds and the service-account
seed). A `Seed:AdminPassword` that fails the 12-char/digit/upper/symbol policy produces: no account,
an `AddToRoleAsync` on an unpersisted user, and — in the generated-password branch — a
`.admin-credentials` file on disk naming an account that does not exist. `roleManager.FindByNameAsync(...)`
results are also null-forgiven at `GetThereAPI/Program.cs:357-358`.

### M8. The journey status sweep loads every journey in the database

`GetThereAPI/Managers/JourneyManager.cs:282-284`

```csharp
var journeys = await _db.Journeys.Where(j => j.Status != JourneyStatus.Cancelled).ToListAsync(ct);
```

Not per-user, not batched, no `Take`. Runs hourly from `TicketExpiryWorker`. The two sibling jobs in
that worker were deliberately written as `ExecuteUpdateAsync`; this one materialises the whole table.

### M9. N+1 in the station reconciliation detail view

`TransitInfoAPI/Managers/StationManager.cs:276-355`

Inside `foreach (var candidate in candidates)`: one query for `rawStopRoutes`, then two more
(`rawDirections`, `stationDirections`) when any line matches. `stationDirections` depends only on the
station `id` and is identical on every iteration — it can be hoisted out of the loop entirely.

### M10. Blocking semaphore wait on the request path

`GetThereAPI/Services/TransitInfoApiClient.cs:56-68`

`InvalidateCachedToken()` uses `_tokenSemaphore.Wait()`, called from `GetRawAsync:164` and
`SendWithAuthAsync:197` — both async request paths. It blocks a thread-pool thread for as long as
another request holds the semaphore, which is the duration of a full login round-trip to
TransitInfoAPI. Under a burst of 401s this is a thread-pool starvation pattern.

### M11. Five `async` methods with no `await` — CI builds these with `-warnaserror`

CS1998, verified by reading each body:

| File | Method |
|---|---|
| `TransitInfoAPI/Managers/FeedManager.cs:622` | `AutoGenerateShapesIfMissing` (also ignores its `ct`) |
| `TransitInfoAPI/Managers/OperatorManager.cs:146` | `GetTypesAsync` |

| `GetThere/ViewModels/ProfileViewModel.cs:269` | `GoToLoginRegister` |

`.editorconfig` suppresses no `CS####` rule, and `build-check.yml` passes `-warnaserror` to both

### M12. Refresh issues a new access token without rechecking the account

`GetThereAPI/Managers/AuthManager.cs:183` · `TransitInfoAPI/Managers/AuthManager.cs:155`

```csharp
var newAccessToken = await _tokenManager.CreateTokenAsync(existingRefreshToken.User);
```

No check that the user is still present, unlocked, or enabled. A locked-out account keeps minting
access tokens for the life of its refresh token. `DynamicClaimsTransformation` narrows the blast
radius by re-reading roles per request, but only for endpoints that carry a policy —
see M13.

### M13. A deleted user stays authenticated

`SharedAuth/DynamicClaimsTransformation.cs:70-72`

When `FindByIdAsync` returns null the transformation returns `null` and adds no claims, but the
principal is still `IsAuthenticated`. Endpoints protected by bare `[Authorize]` — `POST /auth/logout`,
`POST /auth/change-password` in both APIs — still admit the caller.

### M14. New accounts have no wallet

`GetThereAPI/Managers/AuthManager.cs:39-73` · `GetThereAPI/Controllers/WalletController.cs:46-56`

`RegisterAsync` never creates a `Wallet`. The only caller of `EnsureWalletAsync` is `POST /wallet/ensure`.
A client that registers and goes straight to a purchase gets `404 WALLET_NOT_FOUND` from
`TicketingManager.cs:96`, and `GET /wallet` 404s too. The app happens to call `/wallet/ensure` first,
so this is a contract that only holds by client convention.

## What was checked and found sound

Worth recording so the next pass does not re-derive it:

- **`TicketingManager.PurchaseTicketAsync`** — three-stage structure, conditional atomic debit,
  compensating refund with a double-refund guard keyed on the ledger row, idempotency backed by a
  filtered unique index, and `ReconcilePendingPurchasesAsync` closing the crash window. No defect found.
- **`RefreshTokenEvaluator`** — reuse tested before the active check, which is the ordering that makes
  detection work; both APIs route through it.
- **Ticket upload** — sniffed content type (not the declared one) as the allow-list, server-minted
  blob keys, single-use consumption in the same `SaveChanges` as the ticket, and a path-containment
  check that rejects both separators regardless of platform.
- **`MapManager.IsAllowedUpstreamPath`** — a real allow-list, not a filter; the catch-all proxy route
  cannot reach TransitInfoAPI's admin surface.
- **`ExternalFeedSource`** — decompression-bomb ceiling, capped read against a lying `Content-Length`,
  and an internal-address block that covers IPv4-mapped IPv6 and the cloud metadata range.
- **Localization** — English and Croatian `.resx` are at key parity.

## Since resolved

**M2 — reconciliation inside the import transaction.** ✅ Moved outside, on the owner's decision.
It was not the two-line move estimated here: because a failure can no longer roll the import back, it
needed a distinct `FeedImportStatus.ReconciliationPending`, an owning
`FeedManager.ReconcileImportedVersionAsync`, and a `POST /feeds/versions/{id}/reconcile` repair
endpoint. Verified live — 2 515 raw stops reconciled outside any transaction. Tracked as **T18** in
[`audit-transitinfo-2026-07-29.md`](audit-transitinfo-2026-07-29.md).

**M12 — refresh did not recheck the account.** ✅ `GetThereAPI.AuthManager.RefreshAsync` now rejects a
locked-out or missing account before rotating, answering identically to an expired token so it is not
an oracle. Fixed on explicit instruction, which is what `AGENTS.md` requires for the auth pipeline.
*TransitInfoAPI's own `RefreshAsync` still has this — it was out of scope for that instruction.*

**M13 — a deleted user stayed authenticated.** ✅ `DynamicClaimsTransformation` now returns an
unauthenticated principal when the user no longer exists, so bare `[Authorize]` endpoints 401.
This lives in the shared `SharedAuth` project, so the fix necessarily lands in **both** APIs.
