## 🔴 High

### A1. The double-refund guard is a read-then-write race, and two instances will both take it

`GetThereAPI/Managers/TicketingManager.cs:370-372` (the check) · `:388` (the transaction, opened
*after* it) · `GetThereAPI/Data/AppDbContext.cs:76-84` (no unique index)

`RefundAsync` protects itself against crediting a wallet twice by asking whether a refund ledger row
already exists:

```csharp
var alreadyRefunded = await _db.WalletTransactions
    .AsNoTracking()
    .AnyAsync(wt => wt.Type == WalletTransactionType.Refund && wt.ReferenceId == reference, ct);
```

That read happens **outside** the transaction opened sixteen lines later, and there is **no unique
index on `WalletTransactions`** — the entity's configuration declares precision and a foreign key and
nothing else. So the guard is advisory: two callers that interleave between the `AnyAsync` and the
`INSERT` both see `false`, both run `UPDATE Wallets SET Balance = Balance + amount`, and both write a
`Refund` row. The user is credited twice for one debit.

The comment above the guard is explicit that a second attempt is expected — "the live path may fail
partway and leave the purchase Pending, and the reconciliation sweep then picks it up" — so the two
writers are a designed-in pair, not a hypothetical.

**What makes it more than theoretical:** `PurchaseReconciliationWorker`
(`Services/PurchaseReconciliationWorker.cs:46-84`) is a plain `BackgroundService` with no leader
election, no advisory lock, and no `Seed:Enabled`-style opt-out. Commit `e488ccc` ("Make both APIs
safe to run as more than one instance") and the `Seed:Enabled=false` guidance at `Program.cs:367-371`
both say multi-instance is an expected deployment. Two instances sweep the same stranded purchase on
the same tick and refund it twice.

**Failure scenario:** purchase 41 is `Pending` for 6 minutes with a €12 debit. Instances A and B both
tick. Both read no refund row for `ReferenceId = "41"`. Both credit €12. The wallet gains €24 against
a €12 debit, and the ledger shows two `Refund` rows that each claim `BalanceBefore = BalanceAfter -
12` — mutually inconsistent, and the audit trail no longer reconstructs the balance.

**Fix:** a filtered unique index on `WalletTransactions (Type, ReferenceId)` where `ReferenceId IS NOT
NULL`, then let the insert fail and catch it — exactly the pattern the purchase path already uses at
`TicketingManager.cs:168` / `AppDbContext.cs:136-138`. Needs a migration, so it belongs to a session
with a database. Alternatively, and without a migration: move the guard inside the transaction and
make the check-and-insert atomic (`INSERT … WHERE NOT EXISTS`, or an `UPDLOCK, HOLDLOCK` read).

### B1. A 6 KB image can allocate 1.6 GB — no bound on decoded dimensions

`GetThereAPI/Services/Extraction/BarcodeDecoder.cs:47`

```csharp
using var bitmap = SKBitmap.Decode(imageBytes);
```

`TicketUploadManager.MaxFileBytes` bounds the **compressed** upload at 10 MB. Nothing anywhere bounds
the **decoded** bitmap — a grep for `MaxWidth`, `MaxHeight`, `MaxPixels`, `SKImageInfo`, `Resize` or
`Sample` across `GetThereAPI` returns nothing.

A PNG is a compressed format with dimensions in its header. A ~6 KB file declaring 20000 × 20000
decodes to 20000 × 20000 × 4 = **1.6 GB**. It gets worse immediately after:

- `Decode(SKBitmap)` at `:70` calls `bitmap.Copy(SKColorType.Rgba8888)` whenever the source is not
  already RGBA — a **second** full-size buffer.
- ZXing then runs with `TryHarder`, `TryInverted` and `AutoRotate` (`:81-89`) over the whole surface,
  which is unbounded CPU on top of the memory.
- `PdfTicketExtractor.cs:69-78` multiplies it: up to 12 embedded images per PDF, each decoded the
  same way.

`catch (Exception ex)` at `:59` then swallows the resulting `OutOfMemoryException` and returns null,
so the request logs as "no barcode found" while the process is already in an unrecoverable state.

**Reachable now**, unlike A1: ticket import is shipped, and any account holds `importedtickets.create`
by default (`PermissionKeys.UserRoleDefaults:87`). The `Upload` limiter allows 10/minute per user.

The MAUI client downscales camera captures before upload (`GetThere/Services/TicketCaptureService.cs:186-198`),
which is why this has not been seen in normal use — but that is a client-side courtesy, irrelevant to
a direct API call or to a file the user picks from disk.

**Fix:** read dimensions first with `SKCodec.Create` and reject anything beyond a sane pixel ceiling
before decoding, or decode downsampled via `SKImageInfo`. Also narrow the `catch` at `:59` so it stops
swallowing `OutOfMemoryException`.

### A2. `map/index.html` was copied into GetThereAPI, where half of it cannot work

`GetThereAPI/wwwroot/map/index.js:405, 452` — byte-identical to `TransitInfoAPI/wwwroot/map/index.js`
(verified with `diff`)

The page calls its own origin for transit data:

```js
fetch(`/stations/${id}/departures?count=5`).then(r => r.json())
```

GetThereAPI serves no `/stations` route — its transit surface is `/api/map/*`, and the sibling
`public.js:4` correctly uses `const API_BASE = '/api/map/upstream'`. So on GetThereAPI this fetch
404s and the departures panel shows "Failed to load departures", permanently. The same file also
links to `/admin/shape-editor.html` (`:452`), which exists only in `TransitInfoAPI/wwwroot/admin/` —
GetThereAPI's admin directory has no such page.

The file is a verbatim copy of TransitInfoAPI's operator-facing map that was never adapted. It works
in TransitInfoAPI, where those routes exist.

**Fix:** either point it at `/api/map/upstream` and drop the shape-editor link, or delete it from
GetThereAPI — `public.html` is the page the MAUI client actually loads
(`GetThere/Helpers/ApiEndpoints.cs:32`).

### A3. The same map page leaves three feed-controlled fields unescaped

`GetThereAPI/wwwroot/map/index.js:393, 395, 397` and the identical `TransitInfoAPI` copy

`public.js` escapes every one of these; `index.js` escapes only some:

```js
<h2>${props.name || 'Unknown'}</h2>
<div class="info-row"><strong>Onestop ID</strong> ${props.onestopId || '-'}</div>
<div class="info-row"><strong>Country</strong> ${props.countryName || '-'}</div>
```

The file **defines `esc()` at line 434** and uses it for `headsign` and `routeName` — the two fields
H2 of `audit-2026-07-28.md` named — so this is that fix applied to the reported fields on one page
and not to its sibling's remaining three. `name` and `countryName` come from GTFS `stops.txt` and the
country table; `onestopId` is feed-derived.

**Severity qualified honestly:** the CSP added since
(`GetThereAPI/Program.cs:329-334`) sets `script-src 'self' https://unpkg.com` with no
`'unsafe-inline'`, which blocks both injected `<script>` and inline event handlers. So this is markup
injection and defacement rather than script execution *as long as the CSP holds and the page is
served by GetThereAPI*. `TransitInfoAPI`'s copy needs its own header block checked against the same
standard.

### A4. Changing an email address permanently bricks registration for the old one

`GetThereAPI/Managers/ProfileManager.cs:27-32` · `Managers/AuthManager.cs:56, 63-64`

Registration sets `UserName = Email` (`AuthManager.cs:56`). `UpdateProfileAsync` changes the address
with `SetEmailAsync`, which does **not** touch `UserName`. So after user A moves `a@x` → `b@x`, A
still has `UserName = "a@x"`.

Now B registers `a@x`. `FindByEmailAsync("a@x")` returns nothing, so the guard clause passes.
`CreateAsync` then fails with `DuplicateUserName` — and that error is collapsed into silent success:

```csharp
if (result.Errors.All(e => e.Code is "DuplicateUserName" or "DuplicateEmail"))
    return;
```

B is told registration worked. No account exists. B cannot log in, and every retry answers the same
way, forever.

The silent-success branch is right for what it is *for* — not being an account-enumeration oracle —
and should stay. The defect is the stale `UserName`.

**Fix:** `SetUserNameAsync` alongside `SetEmailAsync` in `UpdateProfileAsync`. Note also that
`SetEmailAsync` clears `EmailConfirmed` and no confirmation flow exists anywhere in the solution.

### A5. `SetUserRoleAsync` strips every role before checking the new one exists

`GetThereAPI/Managers/RolePermissionManager.cs:157-180`

```csharp
if (currentRoles.Count > 0)
    await _userManager.RemoveFromRolesAsync(user, currentRoles);

await _userManager.AddToRoleAsync(user, roleName);
```

Three problems in four lines. `roleName` is never validated against the role store, and
`AddToRoleAsync` throws `InvalidOperationException` on an unknown role — after the removal has
already committed. Both `IdentityResult`s are discarded. And there is no transaction, so there is no
path back.

**Failure scenario:** an admin calls the endpoint with `Administrator` instead of `Admin`. The target
user is stripped of all roles, the call returns 500, and the user is left with no role and no
permissions. Doing it to one's own account locks the console.

**Fix:** resolve the role first and 400 if it does not exist; check both results; wrap the pair in a
transaction.

### A6. `UpdateRolePermissionsAsync` can leave a role with no permissions at all

`GetThereAPI/Managers/RolePermissionManager.cs:99-105`

`RemoveClaimAsync` and `AddClaimAsync` each save independently, in a remove-all-then-add-all loop with
no transaction. A failure between the two loops leaves the role stripped. Applied to `Admin`, that is
a lockout of every permission-gated endpoint — and `DynamicClaimsTransformation` re-reads role claims
per request (`SharedAuth/DynamicClaimsTransformation.cs:74-82`), so it takes effect within the 30-second
cache window rather than at next login.

`DeleteRoleAsync:125` has the sibling problem: `DeleteAsync`'s result is discarded, and because
`AppDbContext.cs:45-46` forces **every** foreign key to `DeleteBehavior.Restrict`, deleting a role
that users still hold fails at the database. The caller is told nothing.

### A7. Registration is four writes with no transaction, and the role result is discarded

`GetThereAPI/Managers/AuthManager.cs:56-78`

`CreateAsync` commits on its own. Then `AddToRoleAsync` (result **discarded**, `:69`), then the wallet
insert and audit row in a separate `SaveChangesAsync` (`:75-78`). Any failure after `:57` leaves an
account that exists but has no role, or no wallet — the precise state the comment at `:71-74` says
this code was written to prevent ("Registration used to leave the user without one").

### A8. A `GET` creates a row, and two concurrent first reads collide

`GetThereAPI/Managers/UserSettingsManager.cs:16-30`

`GetSettingsAsync` inserts a `UserSettings` row and saves. `UserId` is uniquely indexed
(`AppDbContext.cs:88`). Two concurrent first-time reads — trivially produced by an app that loads
settings on two pages at startup — race, and the loser gets a `DbUpdateException` surfaced as 500.
A side-effecting GET is also not safely retryable by any intermediary.

### A9. The stranded-purchase sweep reads every pending row, tracked

`GetThereAPI/Managers/TicketingManager.cs:276-280`

No `Take`, no `AsNoTracking`, every five minutes, with `Include(p => p.Adapter)`. This is the shape of
M8 from 07-28, which was fixed for journeys — `JourneyManager.RollUpStatusesAsync:296-339` now batches
with an ordered `Take(RollUpBatchSize)` and a convergence guard. The same treatment applies here.
A backlog only grows when something is wrong, which is exactly when this runs.

### A10. Top-up has no idempotency key, unlike purchase — **[needs a DB]** to confirm the retry window

`GetThereAPI/Managers/WalletManager.cs:44-104`

`PurchaseTicketAsync` takes an `idempotencyKey` backed by a filtered unique index. `TopUpAsync` takes
nothing: a client that retries after a timeout credits the wallet twice. Bounded at
`MaxTopUpAmount = 1000` per call, unbounded across retries. It is admin-gated today and no payment
provider is wired (`:38-42`), which is why this is Medium and not High — but the schema decision wants
making before one is.

### B2. A malformed `pass.json` answers 500 instead of 400

`GetThereAPI/Services/Extraction/PkPassTicketExtractor.cs:57`

```csharp
using var document = JsonDocument.Parse(passJson);
```

This is the one unguarded parse in the pipeline. Every sibling wraps its own: `PdfTicketExtractor.cs:46-54`,
`ICalTicketExtractor.cs:32-43`, and this very file's ZIP open at `:86-91` — all catch and rethrow as

A `.pkpass` whose `pass.json` is invalid JSON, or nests deeper than `JsonDocumentOptions`' default
`MaxDepth` of 64, throws `JsonException` straight past the extractor into the global handler → **500
Internal Server Error** on input the caller fully controls. Every other malformed-file case in this
pipeline is a clean 400.

### B3. `ITicketExtractor.SourceFor` is dead on the server, and the client reimplements it differently

`Services/Extraction/ITicketExtractor.cs:21` · `ImageTicketExtractor.cs:27` ·
`GetThere/Services/TicketImportDraft.cs:47`

`SourceFor` is implemented by all four extractors and called from **nothing but tests** —
`TicketUploadResponse` never carries a source. The MAUI client derives it independently:

```csharp
_ => extraction.PayloadFormat is not null ? ImportSource.QrScan : ImportSource.Photo
```

The server's `ImageTicketExtractor.SourceFor` returns `Photo` unconditionally — while its own doc
comment at `:23-26` describes precisely the scan-versus-photo distinction it does not implement and
the client does. The client's own comment at `TicketImportDraft.cs:26-31` notes the server method
"exists but is never surfaced by the endpoint".

Not cosmetic: `Source` feeds the dedupe hash (`ImportedTicketManager.ComputeDedupeHash:280`). If the
server's mapping were ever wired up as authoritative, the same file would hash differently and dedupe
would silently stop matching every row already stored.

**Fix:** delete `SourceFor` from the interface, or surface it on `TicketUploadResponse` and delete the
client's copy. Two mappings that must agree, one of them unreachable, is the setup that drifts.

### B4. Two admin endpoints have no page-size bound, and page 0 is a 500

`GetThereAPI/Controllers/AdminController.cs:30-31` (`GetUsers`) · `:89-90` (`GetAuditLogs`)


### B5. The audit log is unbounded in the column *and* unbounded in the query

`GetThereAPI/Data/AppDbContext.cs:94-101` · `Entities/AuditLog.cs`

## MAUI client — third pass

### C1. A refresh that rotates server-side but fails client-side poisons the whole token family

`GetThere/Services/AuthService.cs:91-106`

```csharp
var response = await _http.PostAsJsonAsync("auth/refresh", ...);
if (response.IsSuccessStatusCode)
{
    var data = await response.Content.ReadFromJsonAsync<RefreshTokenResponse>(JsonOptions);
    if (data is not null) { /* store both tokens */ return true; }
}
return false;
```

If the server succeeds — rotating the refresh token, setting `ReplacedByToken`, revoking the old one —
but the client then fails to deserialise the body (`data is null`, a truncated response, a parse
error), the method returns `false` **without storing the new token and without clearing the old one**.

SecureStorage now holds a refresh token that the server has marked as replaced. The next
`IsLoggedInAsync` (`:186-194`) presents it again, and `RefreshTokenEvaluator` correctly reads a token
with a replacement as **theft** — `SharedAuth/RefreshTokenEvaluator.cs:46-47` → `ReuseDetected` →
`AuthManager.RefreshAsync:157-169` revokes **every live refresh token the user has**, signing them out
of every device.

The reuse detection is right; the client's failure to persist what it just received is what turns a
transient parse failure into a full session wipe. **Fix:** clear stored tokens when a refresh returns
success-but-unreadable, so the dead token is never presented a second time.

### D3 (Medium). Six inline handlers interpolate data into a JS string, where HTML escaping is the wrong tool

`TransitInfoAPI/wwwroot/admin/operators.page.js:71, 72, 73, 204` ·
`reconciliation.page.js:299, 322`

### D4 (Medium). The 14 content pages have no token refresh at all

`TransitInfoAPI/wwwroot/admin/admin-auth.js:1-17` · `admin-shell.js:80-104`

`admin-shell.js` implements refresh properly — single in-flight request, re-reads the token per call,
retries the 401 once. It is loaded by **`index.html` only**. The other 14 pages load `admin-auth.js`
instead, which does this:

```js
var token = sessionStorage.getItem('auth_token');   // captured once, at load
window.fetch = function (url, opts) { opts.headers['Authorization'] = 'Bearer ' + token; ... }
```

The token is frozen in a closure at page load and there is no 401 handling, no refresh, and no
redirect-to-login on expiry — the redirect at `:3` only fires when there is no token *at load*.

So an operator who spends more than the 15-minute access-token lifetime on `feeds.html`,
`stations.html`, `reconciliation.html` or any of the other 11 finds every subsequent action failing,
with no prompt and no recovery. The refresh token is sitting in `sessionStorage` unused —
`login.page.js:40-42` even stores it with the comment "Needed by `Shell.refresh()`: the access token
expires after 15 minutes, and without this the console drops the operator back here mid-task."

The two scripts are never loaded together, so there is no header-clobbering conflict — the problem is
simply that the good implementation reaches one page out of sixteen.

## What was checked and found sound

Recorded so the next pass does not re-derive it.

- **`MapInboundClaims = false` in both APIs** (`GetThereAPI/Program.cs:113`,
  `TransitInfoAPI/Program.cs:117`). This is load-bearing and easy to lose: `DynamicClaimsTransformation`
  reads `principal.FindFirst("sub")`, and with the default inbound mapping that claim is renamed to
  `ClaimTypes.NameIdentifier`, the lookup returns null, and **dynamic role revocation silently stops
  working** while every test still passes. Worth a regression test.
- **`RefreshTokenEvaluator`** — reuse tested before the active check, which is the ordering that makes
  theft detectable at all; both APIs route through the shared copy.
- **`TicketingManager.PurchaseTicketAsync`** — the three-stage structure holds: everything fallible is
  checked before money moves, the debit is a conditional atomic `UPDATE` whose `rowsAffected == 0` is
  the insufficient-balance path, no transaction or row lock is held across the adapter call, and
  idempotency is enforced by a filtered unique index with the race caught at `:168`. Only the *refund*
  side has the concurrency gap (A1).
- **`JourneyManager.RollUpStatusesAsync`** — I checked whether the batching loop can spin: every
  predicate branch maps to exactly one switch arm, so a row always converges, and the
  `stale.Count < RollUpBatchSize` break bounds it even if one did not. Correct.
- **`TicketExpiryWorker`** — four jobs, each caught independently, so one lock timeout no longer skips
  the other three for a whole interval. Sweep-then-wait ordering is deliberate and right.
- **Upload path** — sniffed magic bytes as the allow-list rather than the declared `Content-Type` or
  filename, extraction before storage so an unreadable file never becomes an orphaned blob, blob keys
  minted server-side, and single-use consumption in the same `SaveChanges` as the ticket.
  `ResolveUploadAsync` scopes the key to the caller's own unconsumed rows, so a stolen key is
  indistinguishable from a made-up one.
- **`ImportedTicketManager.ComputeDedupeHash`** — length-prefixed fields, so a value containing the
  delimiter cannot shift a field boundary; hashed after UTC normalisation, so one logical ticket has
  one hash regardless of how the caller expressed the offset.
- **`AppDbContext`** — the global `Restrict` loop sits **above** the per-entity configuration
  (`:45-46` before `:49`), so deliberate overrides like `AuditLog`'s `SetNull` win. This is the exact
  ordering bug T5 fixed in `TransitDbContext`; this file has it right.
- **Envelope shapes match across the API boundary** — `/realtime/*` returns bare arrays and the client
  deserialises `List<T>`; `/stations`, `/routes`, `/mobility/stations` return `Paginated<T>` whose list

Added by the second pass:

- **`TicketFileSniffer`** — signatures matched against a bounded 32-byte header with every length
  guarded; RIFF disambiguated at bytes 8-11 so a WAV or AVI is not mistaken for WebP; the HEIC brand
